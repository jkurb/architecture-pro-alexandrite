# Архитектурное решение по кешированию

## 1. Мотивация

Операторы MES жалуются на медленную загрузку дашборда — списка заказов с фильтром по статусам и пагинацией. Пагинация и фильтр уже сделаны, но проблема осталась. После инициатив I2 (вынос расчёта цены) и I7 (read-реплика MES DB) из Task1 чтение списка стало дешевле, но остаётся **горячим read-heavy эндпойнтом**: все операторы читают примерно одну и ту же выборку, частота чтений на порядки превышает частоту изменений.

Кеширование закрывает три проблемы:
- **Время ответа дашборда** — hit отдаёт результат за миллисекунды без обращения к БД.
- **Нагрузка на read-реплику** — число SQL-запросов растёт по числу инвалидаций, а не по числу чтений.
- **Всплески одинаковых запросов** при конкуренции операторов за свежие заказы.

**В скоупе кеша:** `GET /orders` (списки с фильтром/пагинацией) и `GET /orders/counts` (счётчики по статусам).
**Вне скоупа:** карточка заказа (редкие чтения), 3D-файлы (отдаются presigned URL из S3), результаты расчёта цены (отдельная задача Pricing Service), каталог Shop (отдельное решение).

## 2. Предлагаемое решение

### 2.1. Серверный или клиентский кеш

Выбран **серверный кеш** (Redis перед MES API).

| Критерий | Клиентский | Серверный |
|---|---|---|
| Разделяемость между операторами | нет | да |
| Hit rate на первом запросе | низкий | высокий |
| Согласованность списка для всех операторов | низкая | высокая |
| Совместимость с моделью «кто первый кликнул» | опасна — операторы видят разные снимки и конкурируют за уже взятый заказ | управляема через единую инвалидацию |
| Контроль памяти и TTL | нет | LRU, TTL на стороне Redis |

Решающий аргумент — модель «кто первый кликнул, тот взял заказ»: клиентский кеш создаёт гонки между операторами. Клиентский HTTP-кеш (`ETag`, короткий `max-age`) допустим как второй слой, но не подменяет серверный.

### 2.2. Паттерн: Cache-Aside

| Паттерн | Решение | Обоснование |
|---|---|---|
| **Cache-Aside** | **Выбран** | Минимальная latency на запись; простая инвалидация по событиям; устойчивость к падению Redis (fallback в БД); естественно обрабатывает изменения статуса из других сервисов (CRM/Shop) через MQ |
| Write-Through | Отклонён | Кешируются **производные представления** (списки, счётчики), а не сами объекты. На каждой записи пришлось бы пересчитывать все страницы всех фильтров — это тот же запрос к БД. Удорожает критичный путь записи (взятие заказа) |
| Refresh-Ahead | Отклонён | Множество ключей (фильтр × страница × сортировка) большое и подвижное; изменения событийные, а не периодические. Refresh по таймеру обновляет уже инвалидированные ключи и не реагирует на реальные события |

### 2.3. Диаграмма последовательности

Диаграмма чтения списка заказов и записи статуса с участием кеша — в отдельном файле: [cache_sequence.puml](cache_sequence.puml).

Ключевые элементы:
- На чтении — `GET` в Redis, при промахе `SETNX`-лок (single-flight), запрос в read-реплику, `SET` с TTL.
- На записи — UPDATE с CAS на ожидаемом статусе (защита от гонок операторов), затем `INCR orders:version` (инвалидация всех списковых ключей одной операцией) и `DEL order:{id}`.
- Событие `OrderStatusChanged` публикуется через outbox в RabbitMQ; Order Service обновляет таймлайн.
- На внешних изменениях (CRM подтверждает заказ) MES API подписан на событие из MQ и инвалидирует свои ключи.

### 2.4. Стратегия инвалидации

**Программная событийная инвалидация по ключу + страховочный TTL**:
- **Программная по событию** — основной механизм. MES API инвалидирует ключи при локальных записях и по событиям из MQ от других сервисов.
- **Версионирование ключей** — списковые ключи содержат версию (`orders:status=X:page=N:v=42`); инвалидация — атомарный `INCR orders:version`, что делает все старые ключи неадресуемыми без `KEYS`/`SCAN`. Старые ключи дотухают по TTL/LRU.
- **Страховочный TTL** — 60 с для списков, 5 мин для счётчиков и карточки. Защита от пропущенных событий, рестартов между UPDATE и публикацией.

| Стратегия | Решение | Обоснование |
|---|---|---|
| **Программная по событию + TTL** | **Выбрана** | Соответствует event-driven архитектуре с RabbitMQ; высокая актуальность; TTL страхует от сбоев доставки событий |
| Только TTL (временная) | Отклонена | Несовместимо с моделью «кто первый кликнул»: устаревший список в течение TTL вызывает гонки. TTL в 1–2 с обесценивает кеш |
| Только по ключу без TTL | Отклонена | MQ даёт at-least-once, но не in-order; при сбое обработчика рассинхронизация может жить часами и обнаружиться по жалобе |
| Программная (Write-Through-обновление) | Отклонена | Перезапись = повторный запрос к БД; не решает кейс изменений из других сервисов |

**Обработка отказов:** при недоступности Redis — fallback в read-реплику; outbox гарантирует at-least-once публикацию события; CAS на UPDATE отлавливает оставшиеся гонки между операторами.

## 3. Альтернативное решение (доп. задание)

| | **Решение 1. Cache-Aside + событийная инвалидация** | **Решение 2. То же + push-обновления клиенту (SSE/WebSocket)** |
|---|---|---|
| Описание | Redis перед MES API. Polling клиента каждые 5–10 с. См. § 2 и [cache_sequence.puml](cache_sequence.puml) | Тот же серверный кеш + постоянный канал MES API → MES UI: после INCR версии сервер пушит обновление, клиент обновляет локальный список без перезагрузки |
| Плюсы | Минимальная инженерная сложность; stateless API; совместим с горизонтальным масштабированием; решает заявленную проблему | Мгновенное появление новых заказов (сотни мс); меньше polling-трафика; уже окно гонки операторов |
| Минусы | Окно устаревания на клиенте равно интервалу polling | Stateful API (sticky sessions либо общая шина); SSE/WS-gateway, переподключения, backpressure; фронтенд-работа в React; сложнее QA |

**Заключение.** Выбрано **Решение 1**. Жалобы операторов — про *скорость загрузки страницы*, а не про *задержку появления новых заказов*; Решение 1 закрывает её без новых компонентов. Инициатива I4 (pull-очередь назначения операторов) заменяет модель «кто первый кликнул»; после I4 ценность push-уведомлений падает. Решение 2 — естественное расширение поверх Решения 1, если жалобы сохранятся.

## 4. Метрики успеха

| Метрика | Цель |
|---|---|
| Cache hit ratio на `GET /orders` | > 80% после прогрева |
| p95 latency `GET /orders` | < 100 мс |
| RPS к read-реплике на эндпойнтах списков | снижение ≥ 5× |
| Доля stale-чтений (CAS-конфликты на UPDATE) | < 0.5% |

Параметры (TTL, размер Redis, гранулярность версионирования) пересматриваются через месяц на основании данных.
