# Выбор и настройка мониторинга в системе

## 1. Мотивация

Текущая ситуация: Яндекс Метрика покрывает поведение пользователей на сайте, но не видит ни B2B-трафик через API, ни внутренние взаимодействия между Shop, CRM, MES и RabbitMQ. По жалобам известно, что заказы зависают и MES тормозит, однако данных о том, **где именно** и **как часто**, у команды нет. Любая инициатива по оптимизации сейчас опирается на догадки.

Внедрение мониторинга закрывает четыре задачи, важные для бизнеса:

1. **Объективная приоритизация.** Команда переходит от планирования «по жалобам» к планированию «по данным». Это снижает риск инвестиций в оптимизацию не того компонента (см. кейс: производственные мощности достаточны, но клиенты не получают заказы — узкое место не в производстве).
2. **Контроль SLA.** Контрактное обязательство «3 недели на заказ» сейчас не измеряется. Без метрик невозможно ни доказать его выполнение партнёрам, ни обнаружить нарушение раньше клиента.
3. **Раннее обнаружение инцидентов.** Текущая модель — «узнаём от пользователей» — приводит к потере B2B-контрактов. Алерты на метриках сокращают MTTD (mean time to detect) с дней до минут.
4. **Планирование мощностей.** Линейный рост в 100 заказов/месяц и взрывной рост B2B требуют упреждающего масштабирования. Без метрик утилизации решение «нужно ли добавлять инстансы» принимается реактивно.

Мониторинг — фундамент для последующих инициатив из плана развития (I2, I3, I4, I7). Без него невозможно ни обосновать их экономику, ни измерить эффект «до/после».

## 2. Выбор подхода к мониторингу

Подход выбирается по типу наблюдаемого компонента и характеру его нагрузки. Применяемые методы — **Четыре золотых сигнала** (Google SRE), **RED** (Том Уилки) и **USE** (Брендан Грегг). Краткая логика выбора:

- **Четыре золотых сигнала** (Latency, Traffic, Errors, Saturation) — для систем, обслуживающих внешних пользователей: добавляет к RED явный сигнал насыщенности, что критично в нашем кейсе.
- **RED** (Rate, Errors, Duration) — для request-driven сервисов, у которых насыщенность измеряется через подлежащие ресурсы (USE на инфраструктуре).
- **USE** (Utilization, Saturation, Errors) — для ресурсов: серверов, БД, очередей. Не применяется к компонентам с активным кешированием.

Применение к компонентам системы:

| Компонент | Подход | Обоснование |
|---|---|---|
| Shop API, CRM API, MES API, Public Order API (после I3) | **Четыре золотых сигнала** | Сервисы напрямую обслуживают пользователей (B2C и B2B). Метод явно рекомендован для API-систем. Включение Saturation принципиально: коренная проблема кейса — насыщение MES API длительными расчётами и B2B-трафиком. Чистый RED показал бы рост latency и ошибок, но не объяснил бы причину. Saturation измеряется через утилизацию CPU/памяти и длину очереди потоков HTTP-сервера. |
| Pricing Service (после I2), API-часть | **RED** | Синхронная часть — приём задачи и возврат id; классический request-driven контур без длительной обработки в этой ветке. Saturation вынесена в воркеры и измеряется через очередь. |
| Pricing Service, воркеры расчёта | **USE** + бизнес-метрики очереди задач | Расчёт занимает 2–30 минут — это batch-нагрузка, для которой RED неприменим. Ключевые показатели: утилизация воркеров, длина очереди задач, длительность расчёта, доля неуспешных задач. |
| Инфраструктура сервисов (EC2-инстансы) | **USE** | Классический случай метода USE: производительность ресурса падает при росте утилизации. Утилизация и насыщение CPU, памяти, диска, сети. |
| Базы данных (Shop DB, MES DB) | **USE** | Ресурс с ограниченной пропускной способностью. Релевантны утилизация CPU/памяти/диска, насыщение пула соединений и I/O, ошибки транзакций. |
| RabbitMQ | **USE** + бизнес-метрики очередей | Очередь — это ресурс: длина очереди = saturation, in-flight = utilization, попадание в DLQ = errors. Дополнительные бизнес-метрики (возраст старейшего сообщения) дают раннее предупреждение о скрытых заторах. |
| Сквозной жизненный цикл заказа | **Четыре золотых сигнала** на бизнес-уровне | Latency = время в статусе, Traffic = поток заказов, Errors = доля просроченных, Saturation = backlog по статусам. На уровне бизнес-процесса техническая декомпозиция RED/USE неинформативна; важна сквозная картина «где задерживается заказ». Основа инициативы I1 из плана. |

Такое разделение даёт три слоя наблюдения: **бизнес-уровень → сервисный уровень (Четыре сигнала / RED) → инфраструктурный уровень (USE)**. При срабатывании алерта на бизнес-уровне можно спускаться к сигналам API-сервиса, а от них — к USE-метрикам подлежащих ресурсов. Saturation на сервисном уровне — это «мостик»: высокая насыщенность API почти всегда корнями уходит в насыщенный ресурс (CPU, пул соединений к БД, пул потоков).

## 3. Метрики

### 3.1. Бизнес-метрики (сквозной жизненный цикл заказа)

Не входят в исходный список, но являются центральной частью мониторинга по результатам анализа Task1 (инициатива I1).

| Метрика | Зачем | Ярлыки |
|---|---|---|
| `order_status_duration_seconds` (histogram) | Время, проведённое заказом в каждом статусе. Прямое измерение SLA «3 недели». Позволяет ответить на главный вопрос бизнеса: «где задерживаются заказы». | `status`, `channel` (B2C / B2B), `partner_id` |
| `orders_in_status_total` (gauge) | Текущее число заказов в каждом статусе (backlog). Saturation на бизнес-уровне: рост означает накопление работы перед стадией. | `status`, `channel` |
| `orders_created_total` (counter) | Поток новых заказов. Traffic-сигнал, базовая величина для нормирования остальных метрик и для планирования мощностей. | `channel`, `partner_id` |
| `orders_sla_breached_total` (counter) | Число заказов, нарушивших SLA по времени в статусе. Error-сигнал на бизнес-уровне; основа для алертов и отчётности перед партнёрами. | `status`, `channel`, `partner_id` |

### 3.2. API-сервисы (Shop, CRM, MES)

Подход — Четыре золотых сигнала. Метрики собираются одинаково для всех трёх сервисов; различия — только в ярлыке `service`. В колонке «Сигнал» указано, к какому из четырёх сигналов относится метрика.

| Сигнал | Метрика | Зачем | Ярлыки |
|---|---|---|---|
| Traffic | RPS for shop / CRM / MES API | Базовая нагрузка; нормирование ошибок и latency; обнаружение аномалий (резкий спад = сбой, резкий рост = атака или вирусный трафик). | `service`, `endpoint`, `method` |
| Traffic | RPS per user (только для shop API и Public Order API после I3) | Детектирование злоупотребления и абьюза квот после открытия публичного API. Прямой вход для рейт-лимитов (инициатива I11). Для CRM/MES внутренних пользователей метрика избыточна. | `service`, `partner_id` / `user_id`, `endpoint` |
| Traffic | Number of simultaneous sessions (только для shop API) | Индикатор активной B2C-аудитории и соотнесения с RPS. Для CRM/MES число операторов и продавцов ограничено и известно; метрика избыточна. | `service` |
| Errors | Number of HTTP 500 (через единый `http_requests_total` с фильтром по `status_code`) | Доля 5xx — основной индикатор отказов сервиса. Алерт при доле > 1% за 5 минут. | `service`, `endpoint`, `method`, `status_code` |
| Latency | Response time, как histogram | p50/p95/p99 latency; p99 — основа для SLO. | `service`, `endpoint`, `method` |
| Saturation | CPU % | Утилизация процессора; совместно с RPS определяет потолок текущего инстанса и момент горизонтального масштабирования. | `service`, `instance` |
| Saturation | Memory Utilisation | Утилизация памяти; выявление утечек (тренд роста при стабильной нагрузке). | `service`, `instance` |
| Saturation | HTTP server thread pool queue length, DB connection pool waiters | Прямой показатель насыщения сервиса: запросы или соединения встают в очередь. Самый ранний сигнал деградации API — раньше, чем рост latency. | `service`, `instance` |


### 3.3. Базы данных (Shop DB, MES DB)

Подход USE.

| Метрика из списка | Зачем | Ярлыки |
|---|---|---|
| Memory Utilisation for shop / MES db | Saturation БД. Высокая утилизация памяти при стабильной нагрузке — индикатор неэффективных запросов или нехватки буферного кеша. Прямо связано с проблемой B2 (медленный дашборд MES). | `db_instance` |
| Number of connections | Saturation пула соединений. Исчерпание пула — частая причина каскадных отказов API. Критично для MES DB, где CRM API ходит в Shop DB (антипаттерн A4). | `db_instance`, `db_name` |
| Size of shop / MES db instance | Capacity. Тренд роста — основа для планирования upscale managed-инстанса. Важно для Shop DB после открытия B2B-канала (рост числа заказов). | `db_instance` |

Добавляются (вне исходного списка, стандартные для PostgreSQL exporter):

| Метрика | Зачем | Ярлыки |
|---|---|---|
| `pg_stat_database_xact_commit_total`, `pg_stat_database_xact_rollback_total` | Errors на уровне БД. | `db_instance`, `db_name` |
| `pg_stat_activity_max_tx_duration` | Обнаружение долгих транзакций, блокирующих дашборд MES. | `db_instance` |
| `pg_replication_lag_seconds` (после внедрения read-реплик, I7) | Контроль лага реплики; реплика непригодна для дашбордов при большом лаге. | `db_instance`, `replica` |

### 3.4. RabbitMQ

Подход USE + бизнес-метрики очередей.

| Метрика из списка | Зачем | Ярлыки |
|---|---|---|
| Number of dead-letter-exchange letters | Прямой индикатор скрытых потерь сообщений между CRM и MES (проблема A6). Любое ненулевое значение требует разбора; алерт на > 0. | `queue` |
| Number of messages in flight | Saturation очереди. Рост означает, что потребитель не справляется. Для очереди расчёта цены — прямая корреляция с пиковой нагрузкой Pricing Service. | `queue` |

Добавляются:

| Метрика | Зачем | Ярлыки |
|---|---|---|
| `rabbitmq_queue_messages_ready` | Длина очереди ожидающих сообщений. | `queue` |
| `rabbitmq_queue_message_oldest_age_seconds` | Возраст самого старого необработанного сообщения. Лучший индикатор зависших заказов в очередях между CRM и MES. | `queue` |
| `rabbitmq_consumers` | Число активных потребителей. Падение до нуля при ненулевой очереди — авария. | `queue` |

### 3.5. Хранилища

| Метрика из списка | Зачем | Ярлыки |
|---|---|---|
| Size of S3 storage | Capacity. 3D-модели — основной объём хранения, тренд позволяет планировать бюджет и применять lifecycle-политики. | `bucket` |

## 4. План действий

Драфт технического задания. Шаги сгруппированы по приоритету; внутри группы — последовательность реализации.

### 4.1. Базовая инфраструктура мониторинга

1. Развернуть time-series базу: **Prometheus** в HA-конфигурации (две реплики, скрейпинг через Service Discovery в Yandex Cloud). Срок хранения — 30 дней «горячих» данных; для long-term — **VictoriaMetrics** или **Thanos** с выгрузкой в S3 (1 год для бизнес-метрик).
2. Развернуть **Grafana** как единый UI: подключить к Prometheus, настроить аутентификацию через корпоративный SSO, организовать папки дашбордов по командам.
3. Развернуть **Alertmanager**: маршрутизация по severity (info → email, warning → Slack, critical → телефонный звонок on-call через PagerDuty или аналог), дедупликация, политики silence на время плановых работ.

### 4.2. Сбор инфраструктурных метрик (USE)

4. Установить **node_exporter** на все EC2-инстансы (Shop API, CRM API, MES API).
5. Подключить экспорт метрик managed PostgreSQL из Yandex Cloud Monitoring в Prometheus (через remote_write или yc-exporter).
6. Подключить **rabbitmq_prometheus** plugin к инстансу RabbitMQ.
7. Настроить экспорт метрик S3-бакета (Yandex Object Storage → Yandex Monitoring → Prometheus).

### 4.3. Сбор сервисных метрик (RED)

8. Интегрировать **Micrometer** (Spring Boot — Shop API, CRM API) и **prometheus-net** (C# — MES API) с эндпойнтом `/metrics`. Включить стандартные метрики HTTP-сервера: `http_server_requests_seconds` (histogram) с ярлыками `method`, `uri`, `status`.
9. Унифицировать соглашения по ярлыкам между сервисами: общий справочник имён `service`, `endpoint`, `method`, `status_code`, `partner_id` — закрепить в внутреннем стандарте.
10. Добавить middleware для извлечения `partner_id` из JWT и проставления в метрики Public Order API (после I3).

### 4.4. Бизнес-метрики жизненного цикла заказа (инициатива I1)

11. Эмитировать события смены статуса заказа из каждого сервиса (Shop, CRM, MES) в общую шину; на стороне Order Service (после I5) или временного агрегатора — вычислять `order_status_duration_seconds` и `orders_in_status_total`.
12. До появления Order Service — собрать промежуточный экспортер: cron-задача, читающая историю статусов из БД и публикующая метрики в Prometheus (Pushgateway). Это даёт быстрый старт без ожидания I5.
13. Создать ключевой бизнес-дашборд в Grafana: «SLA заказов» — backlog по статусам, среднее/p95 время в статусе, доля просроченных. Доступ для продакт-менеджера и руководства.

### 4.5. Алерты

14. Сконфигурировать алерты по приоритетам (см. раздел 5 «План насыщенности»).
15. Описать runbook для каждого алерта: что значит, кому эскалировать, какие первые действия.

### 4.6. Процессы

17. Назначить владельцев дашбордов: каждый сервисный дашборд имеет ответственного из команды.
18. Включить обзор ключевых метрик в еженедельный engineering review.
19. Подготовить шаблон отчёта SLA для бизнеса на основе бизнес-дашборда.

## 5. Показатели насыщенности и реакция (дополнительное задание)

Насыщенность (saturation) — степень исчерпания пропускной способности ресурса. Пороги выбраны с запасом, обеспечивающим время на реакцию до полного отказа.

### 5.1. Сервисные пороги

| Ресурс | Метрика | Warning | Critical | Обоснование порога | Реакция |
|---|---|---|---|---|---|
| CPU EC2-инстанса API | `node_cpu_seconds_total` (1 - idle), 5-мин avg | > 70% | > 85% на 10 мин | При 85% latency деградирует нелинейно (теория очередей); 70% даёт окно для упреждающего масштабирования. | Warning → тикет на capacity review; Critical → автоматическое добавление инстанса (после I7) + алерт в Slack дежурному. |
| Memory EC2-инстанса API | `node_memory_MemAvailable_bytes / MemTotal` | < 25% доступно | < 10% доступно | Ниже 10% риск OOM-kill; 25% даёт время на расследование утечки. | Warning → тикет на профилирование; Critical → перезапуск инстанса по rolling-схеме, алерт on-call. |
| Connection pool БД | `pg_stat_activity_count / max_connections` | > 70% | > 90% | Исчерпание пула вызывает каскадные отказы API. | Warning → разбор источника соединений; Critical → временное расширение пула + алерт on-call. |
| Память БД | Memory Utilisation managed-инстанса | > 75% | > 90% | Выше 90% теряется буферный кеш, запросы уходят на диск. | Warning → план upscale на ближайший maintenance window; Critical → внеплановый upscale managed-инстанса. |
| Размер БД / S3 | Size + тренд | 70% от лимита тарифа | 85% | Linear forecast: оценка времени до достижения лимита по 7-дневному тренду. | Warning → тикет на расширение; Critical → автоматический алерт DevOps и финансовому ответственному. |

### 5.2. Пороги очередей (RabbitMQ)

| Метрика | Warning | Critical | Обоснование | Реакция |
|---|---|---|---|---|
| `rabbitmq_queue_messages_ready` (длина) | Рост > 2× от baseline за 15 мин | > 5× baseline или > 10 000 сообщений | Резкий рост — индикатор отказа потребителя или всплеска входящего трафика. | Warning → уведомление в Slack команде сервиса-потребителя; Critical → on-call + диагностика потребителя. |
| `rabbitmq_queue_message_oldest_age_seconds` | > 5 минут | > 30 минут | Заказы старше 30 минут в очереди расчёта — прямое нарушение пользовательского опыта (расчёт цены ожидается за 2–3 минуты). | Warning → тикет; Critical → on-call, бизнес-эскалация продакт-менеджеру. |
| Number of DLQ letters | > 0 | > 10 за час | Любое попадание в DLQ — потенциальная потеря заказа. | Warning → автоматическое создание тикета с трейсом сообщения; Critical → on-call + блокировка релизов до разбора. |
| `rabbitmq_consumers` для критичных очередей | < ожидаемого | = 0 при ready > 0 | Отсутствие потребителей при наличии сообщений — авария. | Critical → немедленный on-call. |

### 5.3. Бизнес-пороги (SLA заказов)

| Метрика | Warning | Critical | Обоснование | Реакция |
|---|---|---|---|---|
| Время в статусе `PRICE_CALCULATED` без перехода в `MANUFACTURING_APPROVED` | > 4 часа | > 24 часов | Заказ ждёт подтверждения продавца; затягивание — индикатор перегрузки CRM-команды. | Warning → дайджест продакт-менеджеру; Critical → автоматический тикет в CRM-команду. |
| Время от `SUBMITTED` до `SHIPPED` | > 14 дней | > 18 дней | Обязательство «3 недели» = 21 день. 18 дней — последний момент эскалации, чтобы успеть. | Warning → автоматический тикет в Order Service-команду; Critical → эскалация менеджеру по работе с клиентом + автоматическое уведомление клиента. |
| Доля заказов с нарушением SLA за день | > 1% | > 5% | Системная деградация процесса, требующая немедленного разбора. | Warning → дневной отчёт; Critical → инцидент-call с участием инженерной команды и продакта. |

### 5.4. Сервисные пороги RED

| Метрика | Warning | Critical | Реакция |
|---|---|---|---|
| Доля HTTP 5xx по сервису | > 0.5% за 5 мин | > 2% за 5 мин или > 5% за 1 мин | Warning → автоматическое создание тикета; Critical → on-call, возможный rollback последнего деплоя. |
| p99 latency API (по эндпойнту) | > 2× baseline | > 5× baseline | Warning → автоматический разбор top-N медленных эндпойнтов; Critical → on-call. |
| RPS per partner (после I11) | > 80% от квоты | > 100% от квоты | Warning → уведомление партнёру; Critical → автоматическое включение throttling. |

### 5.5. Общие принципы реакции

- **Warning** — рабочее время, тикет в трекер, разбор в течение спринта.
- **Critical** — круглосуточный on-call, выезд по PagerDuty, разбор инцидента в течение часа, postmortem в течение недели.
- Все пороги — стартовые значения. После 1–2 месяцев накопления данных пороги пересматриваются на основе фактических baseline и распределений (P95, P99).
- Алерт без runbook не выпускается в production: каждое срабатывание должно сопровождаться чёткой инструкцией по диагностике.
