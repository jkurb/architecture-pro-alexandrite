# Архитектурное решение по логированию

## 1. Мотивация

### 1.1. Контекст и проблема

Сегодня инциденты в «Александрите» разбираются по обращениям клиентов: пользователь сообщает менеджеру, менеджер — поддержке, поддержка — команде. Между моментом инцидента и его восстановлением проходят часы, иногда дни, а часть проблем не воспроизводится вовсе. Метрики (Task2) показывают, *что* что-то пошло не так и *где* по компонентам, но не отвечают на вопрос *почему*: какое именно сообщение упало в DLQ, какой `order_id` застрял на стадии `PRICE_CALCULATED`, какой партнёр получил `400 Bad Request` и по какой причине. Без логов разбор каждого случая требует ручного дампа БД и опроса разработчиков по нескольким сервисам.

Внедрение централизованного логирования закрывает четыре системные задачи:

1. **Снижение MTTR при разборе инцидентов.** Сейчас восстановление по жалобам клиента занимает дни — команда вручную собирает контекст из трёх систем. Структурированные логи с `correlation_id` сквозь Shop → Pricing → CRM → MES сокращают разбор одного инцидента до минут.
2. **Снижение нагрузки на поддержку и продакт-менеджера.** Поддержка тратит до 40% времени на сбор контекста по жалобам. Самообслуживание поддержки через дашборды поиска по `order_id`/`partner_id` высвобождает это время.
3. **Постмортем-разбор инцидентов и предотвращение повторов.** Без логов невозможен качественный постмортем: восстанавливается только последствие, а не цепочка причин. Логи дают временную картину, которую метрики сглаживают агрегацией.
4. **Аудит и доказательная база.** B2B-партнёры теряют контракты и могут предъявлять претензии по SLA. Аудируемый журнал входящих запросов и переходов статусов заказа — единственное основание для разбора спорных кейсов с партнёром.

### 1.2. Метрики решения

Влияние внедрения логирования оценивается следующими метриками. Базовые значения зафиксированы по текущей наблюдаемой ситуации; целевые — после полного развёртывания.

| # | Метрика | Тип | Базовое значение | Целевое значение | Связь с логированием |
|---|---|---|---|---|---|
| M1 | **MTTR** (Mean Time To Resolve) для инцидентов уровня P1/P2 | техническая | от 12 часов до нескольких суток | ≤ 2 часов | Без логов — реконструкция из БД и опроса. С логами и `correlation_id` — переход к первопричине за минуты. |
| M2 | **Доля «нераскрытых» жалоб клиентов** (закрытых без установления причины) | бизнес | ≈ 25–30% (оценка) | < 5% | Журнал событий заказа позволяет восстановить путь каждого `order_id` независимо от того, обращался ли клиент сразу. |
| M3 | **Время на разбор одного обращения в поддержке** | бизнес | 30–90 минут | 5–10 минут | Поиск по `partner_id`/`order_id` в Logs UI заменяет ручной опрос разработчиков. |
| M4 | **MTTD** (Mean Time To Detect) для ошибок интеграции (например, всплеск 4xx у партнёра) | техническая | часы (через жалобу) | < 5 минут | Алерты на error rate в логах срабатывают раньше, чем партнёр успевает написать. |
| M5 | **Доля B2B-обращений, закрытых с предоставлением доказательной выдачи из журналов** | бизнес | 0% | ≥ 95% | Аудируемый журнал входящих API-запросов и переходов статусов даёт подтверждение SLA в споре с партнёром. |

### 1.3. Приоритизация: что покрывать в первую очередь

Команда не сможет одновременно настроить логирование и трейсинг во всех сервисах. Полное покрытие — это новые SDK-зависимости в каждом приложении, переписывание точек логирования с структурным форматом, согласование контракта `correlation_id` между Java и C#, политика маскирования PII в каждом сервисе. На каждый сервис уходит 1–2 спринта инженерного времени.

Приоритизация выстраивается по двум осям: **частота инцидентов** (там, где жалобы концентрируются) и **архитектурная критичность** (там, где проходит критический путь B2C/B2B-заказа). Обе оси указывают на одни и те же компоненты.

**Очередь 1 (must-have, спринты 1–2).** Покрываются компоненты, через которые проходит критический путь заказа и где сейчас концентрируются жалобы:

- **Public Order API** — внешний контракт с B2B-партнёрами, прямая причина потери контрактов. Логирование здесь даёт аудируемую базу для разбора любого спорного API-вызова.
- **MES API** — точка концентрации жалоб операторов (медленный дашборд) и текущая точка приёма B2B-заказов. Логирование показывает, какие запросы попадают в очередь и почему.
- **Pricing Service** — асинхронный воркер с длинной обработкой (2–30 мин); без логов невозможно понять, на какой задаче зависла очередь и почему расчёт занял 30 минут вместо 3.
- **Order Service** — владелец сквозного жизненного цикла заказа; единственная точка, откуда видна вся цепочка статусов. Логи здесь — основа аудита SLA.
- **RabbitMQ** — события в DLQ сейчас невидимы; ровно здесь «теряются» заказы между CRM и MES (проблема A6 из Task1).

Эти пять компонентов покрывают **>90% сценариев жалоб** при ≈30–40% инженерных усилий полного покрытия.

**Очередь 2 (спринты 3–4).** Shop API, CRM API. Сценарии B2C-фронта обычно воспроизводятся пользователем; критичны для аудита, но не первичный источник «потерянных» заказов.

**Очередь 3 (спринты 5+).** UI-приложения (Shop, CRM, MES Web), 3D Files Storage. Клиентские логи и логи доступа к объектному хранилищу — последний слой; полезны, но не критичны для разбора текущих жалоб.

**Распределённый трейсинг** настраивается параллельно с логированием, но в той же приоритизации: сначала Public Order API → Pricing → MES API (синхронный путь B2B-заказа), затем Shop API → Pricing (B2C-путь), затем остальные. Trace ID — обязательное поле в каждой записи лога с первого же сервиса в очереди 1; это обеспечивает корреляцию метрик, трейсов и логов в любой момент.

## 2. Анализ: какие логи собирать

### 2.1. Источники логов

На схеме [jewerly_c4_logging.drawio](jewerly_c4_logging.drawio) оранжевыми связями выделены компоненты — источники логов. Перечень и обоснование:

| Компонент | Очередь | Что логируем | Зачем |
|---|---|---|---|
| **Public Order API** | 1 | Входящие запросы партнёров, аутентификация, валидация, рейт-лимиты, ответы | Аудит контракта с B2B, разбор споров, обнаружение злоупотребления квотами |
| **Pricing Service** | 1 | Постановка задачи в очередь, старт/завершение расчёта, длительность, события об ошибках расчёта | Анализ долгих расчётов, восстановление пути цены |
| **MES API** | 1 | Изменения статусов производства, назначение операторов, доступ к 3D-файлам, ошибки | Разбор «застрявших» в производстве заказов, анализ модели «who-clicks-first» |
| **Order Service** | 1 | Получение событий из MQ, переходы сквозных статусов заказа, SLA-нарушения | Аудит SLA, корреляция статусов из разных систем |
| **RabbitMQ** | 1 | Сообщения в DLQ, отказы публикации, отказы потребителей, состояние очередей | Расследование скрытых потерь сообщений между CRM/MES/Pricing |
| **Shop API** | 2 | Создание заказа, загрузка 3D-файла, переходы статусов B2C | Аудит B2C-заказов |
| **CRM API** | 2 | Подтверждение производства, действия продавцов, ошибки авторизации | Аудит работы продавцов, разбор задержек на стадии `MANUFACTURING_APPROVED` |
| **3D Files Storage (S3)** | 3 | Access-логи объектного хранилища | Безопасность, отслеживание утечек файлов |
| **Базы данных (PostgreSQL)** | 3 | Slow query log, ошибки, отказ соединений | Корреляция деградации API с проблемами БД |
| **UI-приложения** | 3 | Клиентские ошибки JS, навигация по критическим экранам | Воспроизведение клиентских инцидентов |

### 2.2. Общий формат записи

Все логи — структурированные JSON. Обязательные поля во **всех** сервисах:

```json
{
  "timestamp": "2026-05-17T14:23:11.482Z",
  "level": "INFO",
  "service": "pricing-service",
  "instance": "pricing-service-7f9b-8xq2k",
  "env": "prod",
  "version": "1.34.2",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "correlation_id": "ord-2026-05-17-9f3a",
  "event": "price.calculation.completed",
  "message": "Price calculation completed",
  "context": { "order_id": "ord-9f3a", "duration_ms": 184320 }
}
```

`trace_id` — из OpenTelemetry-контекста, общий с системой трейсинга (Tempo). `correlation_id` — бизнес-ключ заказа, проставляется на первом сервисе и пробрасывается через все границы (HTTP-заголовок `X-Correlation-Id`, AMQP-property `correlation_id`). `event` — машиночитаемое имя события (snake_case с точкой как разделителем доменов), основа для агрегаций и алертов.

### 2.3. Перечень логов уровня INFO

INFO — фиксация бизнес-значимых событий и существенных переходов состояния. Не используется для отладочного «шума».

#### Shop API

| `event` | Контекст |
|---|---|

| `order.file_uploaded` | `order_id`, `file_id`, `file_size`, `file_format` |
| `order.submitted` | `order_id`, `customer_id`, `items_count`, `total_polygons` |
| `pricing.requested` | `order_id`, `pricing_task_id` |

#### Public Order API

|---|---|

| `price.calculation.completed` | `pricing_task_id`, `order_id`, `price`, `duration_ms` |

| `event` | Контекст |
|---|---|

#### RabbitMQ (через системные логи и потребителей)

| `event` | Контекст |
|---|---|

Пример соответствия примеру из задания («изменение статуса заказа: логируем время, идентификатор покупателя, номер заказа») реализован в событии `order.status.changed` в Order Service. Помимо `customer_id` (через `correlation_id` поддаётся выборке заказчика) и `order_id`, в нём всегда есть `from_status`, `to_status` и `time_in_previous_status_ms` — именно эта тройка отвечает на вопрос «где задержался заказ».

### 2.4. Другие уровни логирования

| Уровень | Когда | Примеры | Включён в prod |
|---|---|---|---|
| **TRACE** | Очень детальная трассировка отдельных шагов внутри метода. Используется только локально или временно при отладке конкретной задачи. | Шаги парсинга 3D-модели по полигонам | Нет |
| **DEBUG** | Промежуточные шаги бизнес-операции, состояние объектов. | Содержимое корзины перед расчётом, payload AMQP-сообщения до сериализации | Нет; включается динамически на отдельной поде для расследования |
| **INFO** | Бизнес-события и существенные переходы состояния — см. §2.3. | `order.status.changed`, `partner.order.accepted` | Да, всегда |
| **WARN** | Аномальное, но не блокирующее поведение, требующее внимания, но не немедленной реакции. | Превышение `partner.rate_limit.hit`, ретрай (не последний), время в очереди расчёта > 10 мин, расхождение между ожидаемым и фактическим статусом, использование deprecated-эндпойнта | Да |
| **ERROR** | Операция не выполнена. Бизнес-функция нарушена для конкретного запроса/заказа. | Отказ расчёта цены, отказ публикации в MQ, 5xx-ответ клиенту, попадание сообщения в DLQ | Да |
| **FATAL/CRITICAL** | Сервис не может продолжать работу — failed liveness/readiness, потеря соединения с критичной зависимостью на старте. | Невозможность подключиться к Pricing DB при старте, исчерпание ресурсов JVM перед OOM | Да; всегда триггерит немедленный алерт on-call |

**Правила использования:**
- Уровень WARN — не «лёгкая ошибка», а сигнал «нужно посмотреть в течение дня». Если событие требует реакции в течение часов — это ERROR; если событие штатное (даже редкое) — это INFO.
- Каждый ERROR обязан иметь поле `error_class` и `error_message` со stacktrace в поле `stack` (если применимо). Без stacktrace ERROR-запись бесполезна.
- DEBUG в prod включается **не глобально**, а на конкретной поде через изменение runtime-конфигурации (Spring `LoggingSystem`, Serilog dynamic level switch). Это позволяет расследовать конкретный сценарий без лавины логов.
- Уровни сервиса не привязаны к уровням алертов: алерт на DLQ-сообщение (ERROR) — critical, алерт на 5xx-ответ конкретного эндпойнта (тоже ERROR) — warning. Маршрутизация — задача §3.5.

## 3. Предлагаемое решение

### 3.1. Стек технологий

| Слой | Технология | Обоснование |
|---|---|---|
| Эмиссия в Spring Boot (Shop, CRM, Public Order, Order) | **Logback + Logstash JSON Encoder** | Дефолт Spring Boot. Поддерживает MDC для `correlation_id`/`trace_id`, нативный JSON-encoder, async-аппендер. |
| Эмиссия в C# (MES, Pricing) | **Serilog + Serilog.Sinks.Console** | Стандарт .NET, JSON-форматтер, поддержка `LogContext` для пропагации идентификаторов. |
| Корреляция с трейсингом | **OpenTelemetry SDK** | Единый стандарт. Добавляет `trace_id` и `span_id` в MDC/LogContext автоматически. Делает корреляцию метрик, трейсов и логов «бесплатной». |
| Сбор с подов | **Fluent Bit (DaemonSet)** | Низкое потребление (~10 МБ RSS), нативный Kubernetes-метаданные enricher, поддержка masking-парсера. Альтернатива (Filebeat) тяжелее по ресурсам. |
| Буфер | **Kafka** (или managed Yandex Cloud аналог) | Сглаживает всплески, изолирует storage от падения индексации, позволяет re-ingest при ошибках в pipeline. Существующий RabbitMQ намеренно не переиспользуем: смешивать бизнес-события и операционные логи нельзя — деградация одного потока ударит по другому. |
| Парсинг и маршрутизация | **Logstash** или **Vector** | Vector предпочтительнее (быстрее, ниже потребление). Здесь же — финальное маскирование PII по схеме (см. §3.3), маршрутизация по индексам. |
| Хранение и поиск | **OpenSearch** | См. §4 — выбор по критериям. |
| UI, алертинг, аномалии | **OpenSearch Dashboards + Alerting plugin + Anomaly Detection plugin** | Из коробки, без дополнительного UI-слоя. |
| Long-term storage | **S3 (Yandex Object Storage)** через snapshot-репозиторий | Снимки индексов на S3, lifecycle-политика на бакете для перевода в Cold Storage. |

Компоненты пайплайна в C4-диаграмме помечены оранжевым.

### 3.2. Доработки в приложениях

1. **Стандарт логирования.** Внутренний документ `logging-standard.md` с фиксированным форматом полей (см. §2.2), обязательными `event`-именами и таблицей соответствия бизнес-событий и `event`. Один источник правды для Java и C# команд.
2. **Подключение OpenTelemetry SDK** во все сервисы очереди 1 (даже до полной реализации трейсинга — для пропагации `trace_id` в логи).
3. **Middleware/Filter** для извлечения `correlation_id` из HTTP-заголовка / AMQP-property и помещения в MDC/LogContext на старте обработки запроса. На исходящих вызовах — обратное проставление.
4. **Унификация имён** через библиотеку-обёртку (один артефакт для Java, один для .NET) с предопределёнными методами `LogOrderStatusChanged`, `LogPartnerRequestReceived` и т. д. Это исключает разнобой в `event` и снижает риск утечки PII в произвольный `message`.
5. **Async-аппендеры** во всех сервисах: запись в stdout не должна блокировать обработку запроса. Лимит очереди + политика drop-oldest при переполнении (логи не критичны для бизнес-функции; теряем лог, но не теряем заказ).

### 3.3. Политика безопасности

#### 3.3.1. Чувствительные данные

Объекты, относящиеся к чувствительным данным (с учётом ФЗ-152 и сценариев бизнеса):

| Категория | Примеры | Политика |
|---|---|---|
| ПДн физлиц | ФИО, e-mail, телефон, адрес доставки | **Запрещено** в логах в открытом виде. В контексте — только идентификатор (`customer_id`). |
| Платёжные данные | Номер карты, CVV, токен платёжного провайдера | **Запрещено** во всех видах. Маскируются на четырёх уровнях: SDK, Fluent Bit, ingestor, alerting (паттерн-фильтр на 13–19-значные числа). |
| Аутентификационные данные | Пароли, JWT, API-ключи партнёров, `Authorization`-заголовки | **Запрещено**. Логируем факт `auth_method`, но не значение. |
| Содержимое 3D-моделей | Бинарные данные | Не логируется. Логируется только `file_id`, `file_size`, `polygons_count`. |
| Коммерческие данные партнёров | Цены, объёмы заказов | Логируются (нужны для аудита SLA), но доступ к индексу `logs-partner-*` ограничен ролью `support-partners`. |

#### 3.3.2. Многослойное маскирование

PII не должны попадать в логи в принципе. Защита эшелонирована:

1. **Слой 1 — SDK.** Библиотека-обёртка (§3.2) принимает только идентификаторы, а не сами PII-значения. Программист физически не может залогировать `customer.email` через стандартный API.
2. **Слой 2 — Fluent Bit.** Парсер с regex-фильтрами для номеров карт, e-mail, телефонов. Подозрительные значения заменяются на `***MASKED***`. Это страховка на случай прямого вызова `log.info("...")` мимо обёртки.
3. **Слой 3 — Vector/Logstash ingestor.** Финальное правило маскирования перед записью в индекс. Дубликат слоя 2 — на случай, если Fluent Bit пропустил.
4. **Слой 4 — Audit.** Раз в неделю запускается scheduled-проверка: SQL-запрос (через OpenSearch SQL) ищет в индексе подозрительные паттерны. Найденные записи — это сигнал к разбору причин утечки и доработке слоёв 1–3.

#### 3.3.3. Контроль доступа

Доступ к Logs UI организован через корпоративный SSO с ролевой моделью. Минимально необходимые роли:

| Роль | Кому | Доступ |
|---|---|---|
| `log-viewer-prod` | Дежурный on-call инженер | Все индексы prod, кроме `logs-audit-*` |
| `log-viewer-nonprod` | Все разработчики | Только dev/release |
| `support-tier1` | Сотрудники поддержки | Только `logs-business-*` (события заказа, без технических ERROR/WARN) |
| `support-partners` | Менеджеры по работе с B2B | Только `logs-partner-*` |
| `log-admin` | DevOps, SRE | Полный доступ + конфигурация ILM/RBAC |
| `audit-officer` | Назначенный представитель ИБ | Только `logs-audit-*` (журнал доступа к логам, изменения политик) |

Принципы:
- Принцип минимальных привилегий: разработчик не получает доступ к prod по умолчанию; запрос — через тикет с обоснованием на 24 часа.
- Все обращения к логам (запросы в OpenSearch Dashboards) сами логируются в `logs-audit-*`. Это критично для соответствия требованиям ФЗ-152 («кто и когда смотрел персональные данные»).
- Field-level security в OpenSearch: даже при доступе к индексу `logs-public-order-*` поле `context.email` (если оно случайно туда попало) видно только роли `audit-officer`.

#### 3.3.4. Защита трафика

- Между Fluent Bit и Kafka — TLS с client-cert.
- Между Kafka и Vector — TLS.
- Между Vector и OpenSearch — TLS + базовая аутентификация.
- В S3 (snapshots) — server-side encryption + bucket policy с ограничением источника по IP.

### 3.4. Политика хранения

#### 3.4.1. Структура индексов

Один индекс на сервис, паттерн `logs-{service}-{env}-{YYYY.MM.dd}`. Дополнительно:
- `logs-audit-prod-*` — аудит-журнал (доступ к логам, действия admin).
- `logs-business-prod-*` — отдельный индекс только с бизнес-событиями (`order.status.changed`, `partner.order.accepted`, ...). Сужает выдачу поддержке.
- `logs-partner-{partner_id}-prod-*` — выделенные индексы по крупным партнёрам, с маршрутизацией в ingestor по `context.partner_id`. Это даёт быструю выдачу за конкретного партнёра без полного scan.

#### 3.4.2. Сроки хранения (ILM)

Срок выбран как баланс между ценностью для разбора и стоимостью хранения. Бизнес-события держим дольше технических — они нужны для аудита SLA.

| Индекс | Hot | Warm | Cold (S3 snapshot) | Полное удаление |
|---|---|---|---|---|
| `logs-shop-*`, `logs-crm-*`, `logs-mes-*` | 7 дней | 30 дней | — | 30 дней |
| `logs-public-order-*` | 14 дней | 60 дней | 1 год | 1 год |
| `logs-pricing-*`, `logs-order-*` | 14 дней | 60 дней | 1 год | 1 год |
| `logs-rabbitmq-*` | 7 дней | 30 дней | — | 30 дней |
| `logs-business-*` | 30 дней | 180 дней | **3 года** | 3 года |
| `logs-audit-*` | 90 дней | 1 год | **5 лет** | 5 лет (требование ИБ) |
| `logs-partner-*` (только бизнес-события) | 30 дней | 180 дней | **3 года** | 3 года |

Принципы:
- **Hot** — SSD, full text search, доступно из UI.
- **Warm** — HDD, та же доступность, но дороже по latency.
- **Cold** — snapshot в S3, восстановление по запросу в течение часа.
- **Audit и бизнес-события** хранятся дольше — для разбора споров с партнёрами и претензий по ФЗ-152 (срок исковой давности).

#### 3.4.3. Оценка объёма

Грубая оценка от текущей нагрузки:
- ≈10 000 заказов/месяц × ≈10 событий на заказ = 100 000 бизнес-записей/месяц ≈ 3 GB/мес.
- API-логи (доступ): ≈10 RPS × 7 сервисов × ≈1 KB × 86 400 с ≈ 6 GB/день в prod.
- Общая оценка hot-tier: ≈100–150 GB на 30 дней по основным индексам. Это в пределах одного среднего OpenSearch-кластера из 3 нод.

После открытия B2B-канала (рост заказов в ≈3×) объём логов вырастет до ≈300–450 GB на 30 дней. Это всё ещё небольшая нагрузка для кластера из 3–5 нод, но архитектура заранее предусматривает разделение на hot/warm и обязательную ILM-политику — иначе линейный рост объёма быстро упрётся в бюджет.

### 3.5. От сбора к анализу: алертинг и аномалии

#### 3.5.1. Алертинг по статическим правилам

Каждый алерт описан в формате: условие → severity → реакция. Минимально необходимый набор:

| Алерт | Условие | Severity | Реакция |
|---|---|---|---|
| Сообщение в DLQ | `event=mq.dlq.message` в `logs-rabbitmq-*` за 1 мин > 0 | critical | On-call + автоматическое создание тикета с trace_id |
| Рост 5xx на эндпойнте | Доля ERROR-логов с `status_code>=500` на эндпойнте > 2% за 5 мин | critical | On-call + связанный rollback-плейбук |
| Отказ расчёта цены | `event=price.calculation.failed` > 5 за 5 мин | warning | Тикет в команду Pricing |
| Превышение квоты партнёром | `event=partner.rate_limit.hit` > 10 за минуту от одного `partner_id` | warning | Уведомление менеджеру партнёра |
| FATAL/CRITICAL | Любая запись с `level=FATAL` | critical | On-call немедленно |
| Stuck-order (бизнес) | Заказ в статусе `PRICE_CALCULATED` > 24 часа без `order.status.changed` к `MANUFACTURING_APPROVED` | warning | Тикет в команду CRM |
| Нарушение SLA «3 недели» | Заказ с `time_from_submitted_ms > 18 дней` без `SHIPPED` | warning | Эскалация менеджеру клиента |
| Падение объёма логов сервиса | RPS логов сервиса < 50% от baseline за 10 мин | warning | Возможна авария сервиса или ingest-пайплайна |
| Отсутствие новых логов | Сервис не пишет ничего > 5 мин | critical | Сервис мёртв или потерял связь с Fluent Bit |
| Утечка PII | Скрипт-аудитор (§3.3.2) нашёл подозрительный паттерн в индексе | critical | Тикет в ИБ + блокировка релизов до исправления |

Все алерты идут через Alertmanager (см. Task2), маршрутизация по severity не дублируется в OpenSearch Alerting. Для алертов из OpenSearch — webhook в Alertmanager.

#### 3.5.2. Поиск аномалий

Статические правила не покрывают «4 → 10 000 заказов за секунду» и похожие сценарии — порог невозможно задать заранее. Решение — OpenSearch **Anomaly Detection plugin** (RCF, Random Cut Forest).

Детекторы аномалий первой очереди:

| Детектор | Признаки | Что обнаруживает |
|---|---|---|
| `orders_created_rate` | RPS события `order.initiated` (и `partner.order.accepted`) | Внезапный всплеск (DDoS, бот-атака конкурента, баг массового создания) или провал (упал Shop API) |
| `partner_request_rate_per_partner` | RPS по `partner_id` | Аномалия отдельного партнёра — раньше чем сработает rate-limit |
| `error_rate_per_service` | Доля ERROR/WARN от общего объёма логов сервиса | Скрытая деградация без срабатывания 5xx-порога |
| `pricing_duration_p99` | `duration_ms` события `price.calculation.completed` | Деградация воркеров, скрытая утечка ресурсов |
| `auth_failure_rate` | Частота ошибок аутентификации в Public Order API | Подбор API-ключей, утечка credentials партнёра |

Детекторы обучаются на 14-дневном окне, сравнение в реальном времени, чувствительность настроена так, чтобы давать ≤5 ложных срабатываний на детектор в неделю (балансируется после первых двух недель работы).

#### 3.5.3. Корреляция с метриками и трейсами

Поскольку `trace_id` идентичен в логах и в Tempo, в OpenSearch Dashboards настраивается deep-link: клик на `trace_id` в записи лога → открытие соответствующего trace в Tempo UI. Обратное направление — из Grafana: дашборды метрик содержат ссылку «открыть логи за этот интервал по этому сервису» с предзаполненным запросом в OpenSearch Dashboards. Это превращает три раздельных инструмента в единую среду расследования.

#### 3.5.4. Runbook-обязательность

Аналогично метрикам (Task2), ни один алерт не выпускается в prod без runbook. Runbook содержит:
- Что значит срабатывание (бизнес-смысл).
- Кому эскалировать.
- Какие первые три запроса в OpenSearch Dashboards выполнить для диагностики (с заготовленными ссылками).
- Где смотреть связанные метрики и трейсы.

## 4. Дополнительное задание: выбор технологии

### 4.1. Критерии выбора

Критерии формулируются из требований конкретного проекта и стоимости владения. Не каждая «звезда» рынка подходит — важно соответствие масштабу команды и нагрузке.

1. **Стоимость владения.** Включает лицензию, инфраструктуру и операционные затраты команды (один DevOps на всю компанию — критичное ограничение).
2. **Контроль над данными и место хранения.** Бизнес работает в РФ, чувствительные данные не могут уходить в зарубежные облака без правового анализа. Self-hosted и Yandex Cloud — допустимо; SaaS в зарубежной юрисдикции — требует отдельной экспертизы.
3. **Скорость поиска и удобство UI.** Поддержка должна искать по `order_id` за секунды без подготовки. Сложный язык запросов — барьер для адопции.
4. **Алертинг и обнаружение аномалий из коробки.** Внешний интегратор увеличивает время реакции и количество компонентов под обслуживание. ML-детектор аномалий — необходимый, а не желательный пункт (см. §3.5.2).
5. **Интеграция с экосистемой Prometheus/Grafana/OpenTelemetry.** Корреляция метрик-трейсов-логов через `trace_id` уже заложена в архитектуру (Task2 + Task4). Технология не должна требовать переписывания этой связки.
6. **Масштабирование под рост B2B-нагрузки.** Объём логов в перспективе 12 месяцев — до 0.5 ТБ/месяц hot-tier. Технология должна горизонтально масштабироваться без архитектурных переделок.
7. **Зрелость и риск дальнейшего развития лицензии.** Изменения лицензионной политики (как у Elastic в 2021) могут заблокировать развитие.

### 4.2. Сравнение технологий

| Критерий | **ELK (Elasticsearch + Kibana)** | **OpenSearch** | **Splunk** | **Grafana Loki** |
|---|---|---|---|---|
| **Лицензия** | Elastic License 2.0 / SSPL (не OSI-open-source) | Apache License 2.0 (AWS fork) | Проприетарная | AGPL-3.0 (open-source) |
| **Стоимость владения** | Бесплатное ядро, но платные критичные фичи (Security, Alerting, ML); подписка от $95/мес за ноду | Полностью бесплатна, оплата только инфраструктуры | Очень высокая: лицензия на объём индексируемых данных, ≈$1800/ГБ/год | Бесплатна; экономия за счёт индексации только меток |
| **Юрисдикция** | Self-hosted (OK для РФ) или Elastic Cloud (EU/US — спорно) | Self-hosted в Yandex Cloud — OK | Self-hosted возможен; Splunk Cloud — США (неприемлемо) | Self-hosted в Yandex Cloud — OK |
| **Поиск и UI** | Зрелый Kibana, лучшая в классе аналитика, KQL — низкий порог входа | Дашборды (fork Kibana ~7.10) — функционально близки, отстают по фичам последних версий | Лучший в классе UI и язык SPL; «золотой стандарт» | LogQL — мощный, но без full-text по умолчанию; нацелен на logs+labels модель |
| **Алертинг + ML-аномалии** | Платные плагины (X-Pack) | Из коробки бесплатно: Alerting plugin, Anomaly Detection plugin (RCF) | Из коробки, премиум-класса, но дорого | Алертинг через Grafana; ML — внешний |
| **Интеграция OpenTelemetry / Grafana** | OK через Elastic APM; Grafana — через datasource | OK через OpenTelemetry; Grafana — через datasource | Через коннектор; не нативно | Нативная (один вендор) |
| **Масштабирование** | Зрелое, проверенное в больших инсталляциях | То же ядро Lucene — масштабируется аналогично | Зрелое, но требует серьёзного бюджета | Проще для меток+пр.; меньше подходит для произвольного full-text |
| **Зрелость и риск лицензии** | Высокий: уже было изменение лицензии в 2021 | Под Linux Foundation (2024), низкий риск | Стабильный коммерческий поставщик | Стабильный (Grafana Labs) |

### 4.3. Обоснование выбора — OpenSearch

**Выбираем OpenSearch.**

Главные причины:

1. **Стоимость.** Pricing-сервис, рост B2B-нагрузки и линейный рост заказов означают: в горизонте года объём логов вырастет в 3–5×. Splunk при таком росте обойдётся в ≈$50–100 тыс./год за лицензию — для компании с 8-инженерной командой это неприемлемо. Elastic с платными плагинами тоже даёт TCO на порядок выше, чем self-hosted OpenSearch.
2. **Алертинг и аномалии из коробки.** В Elastic ML и Alerting — это X-Pack (подписка). В OpenSearch — Apache 2.0, бесплатно. Это критично, потому что детектор аномалий (§3.5.2) — обязательная часть решения, а не nice-to-have.
3. **Юрисдикция.** Self-hosted OpenSearch разворачивается на Yandex Cloud в той же инфраструктуре, что и остальные сервисы. Никаких дополнительных юридических вопросов.
4. **Совместимость с экосистемой.** OpenSearch использует тот же Lucene под капотом, что и Elastic; миграция Filebeat/Logstash → Fluent Bit/Vector тривиальна. Grafana как unified UI продолжает работать (OpenSearch datasource).
5. **Низкий лицензионный риск.** Apache 2.0 + Linux Foundation. История Elastic с SSPL делает их продукт менее предсказуемым в долгосроке.

**Минусы выбора, которые принимаем:**
- Отставание от Elasticsearch по самым новым фичам (на 6–12 месяцев). Для нашего сценария — не критично; ничего из «последнего» нам не нужно.
- Дашборды (fork Kibana) визуально отстают от современного Kibana — операторы поддержки не заметят, разработчики переживут.
- Loki был бы дешевле в хранении, но full-text search без индексации полей сильно ограничивает сценарий «найти заказ по `order_id`» — для нашей задачи поиска по бизнес-полям OpenSearch удобнее.

**Сравнение с альтернативами:**
- **ELK** — отказываемся из-за платных критичных фич (ML, Alerting) и риска лицензии. Если в будущем компания выйдет за пределы возможностей OpenSearch (что маловероятно в горизонте 2 лет), миграция к Elastic Cloud остаётся технически возможной.
- **Splunk** — отказываемся из-за стоимости и юрисдикции. Может рассматриваться, если компания войдёт в крупный enterprise-сегмент с соответствующими бюджетами.
- **Loki** — рассматривался как backup; отказываемся из-за слабой поддержки full-text-поиска по контексту. Возможен в качестве дополнения для долгосрочного хранения с низкой стоимостью, если появится такая потребность.
