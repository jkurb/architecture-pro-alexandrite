# Архитектурное решение по логированию

## 1. Мотивация

Инциденты сегодня разбираются по обращениям клиентов: ручной дамп БД и опрос разработчиков по трём системам занимают часы и дни. Метрики из Task2 показывают *где* проблема, но не *почему* — какой `order_id` застрял, какой партнёр получил ошибку. Структурированные логи закрывают пробел и дают доказательную базу для споров с B2B.

| # | Метрика | Тип | Базовое | Цель |
|---|---|---|---|---|
| M1 | MTTR для инцидентов P1/P2 | техническая | от 12 ч | ≤ 2 ч |
| M2 | Доля «нераскрытых» жалоб | бизнес | ≈ 25–30% | < 5% |
| M3 | Время разбора одного обращения в поддержке | бизнес | 30–90 мин | 5–10 мин |
| M4 | MTTD ошибок интеграции (всплеск 4xx у партнёра) | техническая | часы | < 5 мин |
| M5 | Доля B2B-обращений с доказательной выдачей из логов | бизнес | 0% | ≥ 95% |

**Приоритизация.** Команда не покроет всё одновременно.
- **Очередь 1 (спринты 1–2):** Public Order API, MES API, Pricing Service, Order Service, RabbitMQ — пять компонентов закрывают >90% жалоб при ≈30% усилий полного покрытия.
- **Очередь 2:** Shop API, CRM API (аудит B2C).
- **Очередь 3:** UI, S3 access logs, slow query log БД.

Distributed tracing разворачивается параллельно; `trace_id` — обязательное поле с первого сервиса.

## 2. Что логировать

Источники и пайплайн — на схеме [jewerly_c4_logging.drawio](jewerly_c4_logging.drawio) (оранжевый — компоненты пайплайна, пунктир — поток логов от сервисов).

**Формат записи** — структурированный JSON, обязательные поля везде:

```json
{ "timestamp": "...", "level": "INFO", "service": "pricing-service", "env": "prod",
  "trace_id": "...", "correlation_id": "ord-9f3a",
  "event": "price.calculation.completed",
  "context": { "order_id": "ord-9f3a", "duration_ms": 184320 } }
```

`trace_id` — из OpenTelemetry-контекста, `correlation_id` — бизнес-ключ заказа, пробрасывается через HTTP-заголовок и AMQP-property. `event` — машиночитаемое имя.

### INFO-события

| Сервис | `event` |
|---|---|
| Shop API | `order.initiated`, `order.file_uploaded`, `order.submitted`, `pricing.requested` |
| Public Order API | `partner.request.received`, `partner.request.authenticated`, `partner.order.accepted`, `partner.rate_limit.hit` |
| Pricing Service | `price.task.enqueued`, `price.calculation.started`, `price.calculation.completed` |
| CRM API | `order.manufacturing.approved`, `order.closed` |
| MES API | `order.manufacturing.started`, `order.manufacturing.completed`, `order.packaging.started`, `order.shipped` |
| Order Service | `order.status.changed` (`from_status`, `to_status`, `time_in_previous_status_ms`, `customer_id`, `order_id` — реализация примера из задания), `order.sla.evaluated` |
| RabbitMQ | `mq.message.published`, `mq.message.consumed`, `mq.dlq.message` |

### Другие уровни

| Уровень | Когда | В prod |
|---|---|---|
| **TRACE/DEBUG** | Детальная отладка конкретного сценария. | Нет; DEBUG включается динамически на одной поде. |
| **INFO** | Бизнес-события и переходы состояния. | Да, всегда. |
| **WARN** | Аномалия без блокировки: рейт-лимит, ретрай, время в очереди > 10 мин. Реакция в течение часов. | Да. |
| **ERROR** | Операция не выполнена для запроса/заказа: отказ расчёта, 5xx, попадание в DLQ. Обязательны `error_class` и `stack`. | Да. |
| **FATAL** | Сервис не может продолжать работу. | Да; немедленный алерт on-call. |

## 3. Предлагаемое решение

### Стек

| Слой | Технология |
|---|---|
| Эмиссия (Java / C#) | Logback + Logstash JSON Encoder / Serilog |
| Корреляция с трейсами | OpenTelemetry SDK |
| Сбор с подов | Fluent Bit (DaemonSet) |
| Буфер | Kafka (отдельный от RabbitMQ — бизнес-события и логи не должны мешать друг другу) |
| Парсинг, маскирование, маршрутизация | Vector |
| Хранение и поиск | OpenSearch (обоснование — §4) |
| UI, алертинг, аномалии | OpenSearch Dashboards + Alerting + Anomaly Detection |
| Long-term | Snapshot в S3 |

### Безопасность

**Запрещены в логах:** ПДн (ФИО, e-mail, телефон, адрес), платёжные данные, токены, пароли, API-ключи, содержимое 3D-моделей. В контексте — только идентификаторы (`customer_id`, `file_id`).

**Маскирование в три слоя:** библиотека-обёртка над логгером (PII нельзя передать через API) → regex-парсер в Fluent Bit → финальное правило в Vector. Еженедельный аудит-скрипт ищет пропущенные паттерны.

**Доступ** — через корпоративный SSO. Роли: `log-viewer-prod` (on-call, все prod кроме audit), `support-tier1` (только `logs-business-*`), `support-partners` (только `logs-partner-*`), `log-admin` (полный + ILM/RBAC), `audit-officer` (только `logs-audit-*`). Обращения к Logs UI сами логируются в `logs-audit-*` (требование ФЗ-152). Field-level security маскирует случайные PII даже при наличии доступа к индексу.

### Хранение

Один индекс на сервис: `logs-{service}-{env}-{YYYY.MM.dd}`. Отдельно: `logs-business-*` (бизнес-события для поддержки), `logs-partner-{partner_id}-*`, `logs-audit-*`.

| Индекс | Hot | Warm | Cold (S3) | Удаление |
|---|---|---|---|---|
| Технические (Shop, CRM, MES, RabbitMQ) | 7 дн | 30 дн | — | 30 дн |
| Pricing, Order, Public Order | 14 дн | 60 дн | 1 год | 1 год |
| `logs-business-*`, `logs-partner-*` | 30 дн | 180 дн | 3 года | 3 года |
| `logs-audit-*` | 90 дн | 1 год | 5 лет | 5 лет |

Бизнес-события и аудит держим дольше — для разбора споров и срока исковой давности по ФЗ-152.

**Объём.** ≈10 000 заказов/мес × 10 событий + API-логи ≈ 100–150 ГБ hot-tier на 30 дней. С ростом B2B в 3× — 300–450 ГБ. Кластер из 3–5 нод OpenSearch.

### Алертинг и аномалии

Статические алерты идут через Alertmanager (webhook из OpenSearch Alerting). Ни один алерт не выпускается без runbook.

| Алерт | Условие | Severity |
|---|---|---|
| Сообщение в DLQ | `mq.dlq.message` > 0 за 1 мин | critical |
| Рост 5xx | доля > 2% за 5 мин на эндпойнте | critical |
| Отказ расчёта | `price.calculation.failed` > 5 за 5 мин | warning |
| Превышение квоты партнёром | `partner.rate_limit.hit` > 10/мин | warning |
| Stuck-order | без `order.status.changed` > 24 ч в `PRICE_CALCULATED` | warning |
| Нарушение SLA «3 недели» | > 18 дн без `SHIPPED` | warning |
| Отсутствие логов сервиса | < 50% baseline за 10 мин | critical |
| Утечка PII | срабатывание аудит-скрипта | critical |

**Аномалии** — OpenSearch Anomaly Detection (RCF, обучение на 14 дней). Детекторы первой очереди: RPS создания заказов (защита от «4 → 10 000 за секунду»), RPS по `partner_id`, доля ERROR по сервисам, p99 длительности расчёта, частота ошибок аутентификации в Public Order API.

**Корреляция.** Общий `trace_id` даёт deep-link «лог → trace в Tempo» и «график в Grafana → логи за интервал».

## 4. Выбор технологии (доп. задание)

**Критерии:** (1) стоимость владения с учётом одного DevOps; (2) юрисдикция данных (ФЗ-152); (3) скорость поиска и порог входа в UI для поддержки; (4) алертинг и ML-аномалии из коробки; (5) совместимость с Prometheus/Grafana/OpenTelemetry; (6) масштабирование до 0.5 ТБ/мес hot-tier; (7) лицензионный риск.

| Критерий | ELK | **OpenSearch** | Splunk | Loki |
|---|---|---|---|---|
| Лицензия | Elastic License 2.0 / SSPL | **Apache 2.0** | Проприетарная | AGPL-3.0 |
| Стоимость | Бесплатное ядро, платные критичные плагины | **Полностью бесплатна** | ≈$1800/ГБ/год | Бесплатна, дёшево по меткам |
| Юрисдикция | Self-hosted OK; Cloud — EU/US | **Self-hosted в Yandex Cloud OK** | Splunk Cloud — США | Self-hosted OK |
| Поиск/UI | Зрелый Kibana, KQL | **Dashboards (fork Kibana 7.10)** | Лучший SPL, премиум | LogQL без full-text по умолчанию |
| Alerting + ML | Платно (X-Pack) | **Бесплатно из коробки** | Премиум | Алерты через Grafana, ML внешний |
| OTel/Grafana | OK | **Нативно** | Через коннектор | Нативно |
| Масштаб | Зрелое | **То же ядро Lucene** | Дорого, но зрело | Слабее для full-text |
| Риск лицензии | Высокий (прецедент 2021) | **Низкий (Linux Foundation 2024)** | Стабильный коммерческий | Стабильный |

**Выбор — OpenSearch.** Apache 2.0 с включёнными ML/Alerting (экономия по сравнению с Elastic X-Pack), self-hosted в Yandex Cloud закрывает юрисдикцию, то же ядро Lucene даёт совместимость и масштаб Elasticsearch, низкий лицензионный риск.

**Минусы (принимаем):** отставание от Elasticsearch по новым фичам на 6–12 месяцев, UI визуально проще современного Kibana.

**Почему не остальные.** ELK — платные критичные плагины и риск лицензии. Splunk — стоимость и юрисдикция Splunk Cloud. Loki — слабый full-text по контексту, неудобен для поиска по бизнес-полям; возможен позже для дешёвого long-term-хранения.
